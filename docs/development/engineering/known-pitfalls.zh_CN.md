# 已知坑与验证盲区

抽取应用框架、拆分仓库、做真机验收时实际踩到的失败模式。每条给出症状、
常规检查为什么没能发现、防范规则、以及现在如何检测。规范本身在
[`coding-conventions.zh_CN.md`](coding-conventions.zh_CN.md) 与
[`../ai-guide.zh_CN.md`](../ai-guide.zh_CN.md);本文记录这些规则背后的原因。

## 1. 门户注入标记劫持了它自己

**症状。** 配网门户能打开,但页面里应用的配置卡片整个不见了。其他界面不受
影响,固件编译通过,主机测试全绿。

**原因。** `handler_index` 用朴素的首个子串匹配把应用片段替换进页面。模板里
任何更早出现该标记字面量的地方——最容易的是一段解释注入点位置的 HTML 注释
——都会成为匹配目标。片段被写进那条注释,真正的容器仍留着原始标记。

**门禁为什么没发现。** 出现在响应文档里的字符串替换,对编译器、主机测试和
固件构建都是不可见的。只有从运行中的设备把页面取下来才看得见。

**规则。**

- 注入标记在模板里必须恰好出现一次。
- 公共助手必须定义在注入点之前的、更早的 script 块里。否则片段的内联
  `<script>` 执行时助手还不存在,而且失败是静默的。
- 片段不得重复声明这些助手。全局 `const` 在两个经典 script 块里重复声明
  会抛 `SyntaxError`,两个块一起失效。

**检测。** `tests/test_portal_template.py` 断言以上三条,并已纳入框架门禁;
该测试经过反向验证,标记重复时确实会失败。`handler_index` 另外会统计标记
出现次数,不等于 1 时打 `ERROR`,让回归在设备日志里显形,而不是只在浏览器里
才能发现。

## 2. 门禁全绿不等于页面正确

任何对 HTML、CSS 或门户 JavaScript 的改动,在从运行中的设备取回页面之前都
不算验证过。必须与构建结果分开报告:

```text
Build:        PASS
Host tests:   PASS
Device tests: NOT RUN   <-- 门户标记与注入仍未验证
```

取页面很便宜——门户是常驻的 80 端口 HTTP,地址就显示在屏幕上。做就是了。检查
三件事:注入的片段确实落在容器内部、没有残留原始标记、公共助手出现在片段之前。

## 3. 框架里还有业务词汇,就不算抽干净

框架是从单个应用里抽出来的,C 代码里看着已经干净,但门户 HTML 模板里仍然留着
该产品的组织发现 UI、它的私有端点、导出文件名里的品牌串和字段名。同一个功能
存在两份实现:一份在框架模板里,一份在应用卡片里。而框架那份是**死的**——它调用
了没有任何处理器注册的端点,也引用了并不存在的 DOM 节点,所以不会有任何显式
失败。

**规则。**

- 只有当框架目录里不含任何业务词汇、字段名、品牌串(包含标记)时,才算抽完。
- 框架里的死应用代码比没有更糟:它把一个应用从来就没有的功能写成了既成事实。
- README 承诺了却没有处理器服务的功能是缺陷,不是占位。返回一个可读的错误,
  好过让页面撞上一个无解释的 404;也确实不要去臆造缺失的后端。

**检测。** `tests/test_portal_template.py` 会拒绝模板里的业务词汇。以后新增
共享素材时,补上同类断言。

## 4. 先读设备分区表,再决定刷写范围

合并镜像写 `0x0` 会重置已存配置;在各自分区偏移处写组件镜像可以保留配置。没有
证据就选,轻则丢设置,重则把应用写到了不属于它的位置。

写组件镜像前,先读出设备的分区表,与本次构建的分区表逐字节比对。字节一致说明
布局未变,分段刷写是安全的。把这个比对结果写进交付报告。

## 5. esptool 4.x 的命令形态变了

- `write_flash` 的 flash 选项要放在子命令**之后**:
  `esptool --chip esp32c3 -p PORT write_flash --flash_mode dio --flash_size 8MB --flash_freq 80m 0x0 file.bin`
- `read_flash` 的参数顺序是地址、大小、文件名:
  `esptool --chip esp32c3 -p PORT read_flash 0x9000 0x6000 out.bin`
- 参数错误发生在解析阶段,什么都没写。先读错误信息再重试——被拒绝的命令
  根本没碰到设备。

## 6. 备份要读两次才算数

单次读成功不能证明备份可用。把同一分区读两次到不同文件,比对哈希,之后才
可信。报告里带上哈希,将来还原时才能核对。

原始镜像旁边再留一份可读副本。原始分区转储里是明文凭据,不是可读的清单;
门户的 `/api/config/export` 才是受支持的可读形式。要分享的副本一律脱敏,
原始镜像不要进版本控制。

## 7. 局部导入会清空热点列表

`apply_import_root` 无条件重建热点表。如果提交的 JSON 里没有 `networks` 数组,
列表会被存成空,所有已保存热点全部丢失,而请求仍返回成功。完整导出往返是安全的,
因为导出总带这个数组;手写或局部的 payload 不安全。

在改掉之前,把导入 payload 里缺失的 `networks` 当作"保持原样"而不是"清空"。
在那之前,只导入完整的导出文件。

## 8. 搬文件会连带弄坏别的东西

把框架和应用拆开时,只是挪了文件位置,却弄坏了四处与搬迁看似无关的地方:

- 某个检查脚本从自身路径推导仓库根,于是复用它的应用仓检查的是框架仓;
- 必需文件清单还在要求框架已不再拥有的构建输入;
- 主机测试用写死的相对路径 `#include` BSP 源码;
- 文档链接指向了已移动的路径,或指向属于另一个仓的文件。

任何搬迁之后,都要在脚本、测试和文档里 grep 旧路径,并且在**两个仓**都跑一遍
门禁。框架如果连自己的门禁都跑不起来就没有意义,所以要验证框架仓能独立通过,
而不只是从应用仓里通过。
